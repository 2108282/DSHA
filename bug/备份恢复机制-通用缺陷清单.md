# 备份/恢复机制 — 通用缺陷清单（产品级）

> 视角：不针对单台设备，任何用户在任意设备上使用「备份→恢复」都应可靠。
> 依据：实测复现 + 配置文件证据 + 崩溃/错误日志。

---

## 问题 1（核心）：备份包内联本机绝对路径依赖，跨设备恢复必然失败

**现象**：恢复备份后 dsh web 启动失败：
```
Error: dsh: cannot resolve profile bundle "dsh-files" from the dsh installation
or /root/.dsh/profiles/web; run 'dsh plugin --profile web install' ...
```

**证据**（profile package.json）：
```json
"dsh-files": "link:/root/plugin-src/dsh-files",
"dsh-undo-savepoint": "link:/root/plugin-src/dsh-undo-savepoint"
```

**根因**：备份包内的插件依赖是 `link:` + **本机绝对路径**。备份到另一台设备后：
- 目标设备的 `/root/plugin-src/` 不存在（甚至用户目录不同）
- 恢复流程把配置原样写入 → 重启 dsh 时 `resolveBundleDir` 找不到包 → 启动失败

**影响**：任何含本地路径插件（link: 依赖）的备份，跨设备恢复 100% 失败。**这是通用缺陷，不是个例。**

**修复建议**：
1. **备份时内联插件代码**：把 `link:` 依赖指向的插件目录实际内容打进备份包，恢复时在目标设备重建（按目标设备路径重映射）
2. **或备份时规范化依赖**：`link:` 依赖若有 registry 版本 → 改写为 `^x.y.z`；无 registry 版本 → 必须内联
3. **恢复时依赖预检**：解压后校验所有 bundle 可解析，缺失则自动安装或明确提示（参照 dsh-undo-savepoint 的跨机迁移方案：预检 + 明确提示）

---

## 问题 2：恢复流程「写配置 → 重启」之间无依赖就绪步骤（时序竞态）

**现象**：恢复备份后（即使同一台设备）重启 dsh web 也偶发 bundle 解析失败；重试或手动 `dsh plugin install` 后成功。

**根因**：App 恢复流程（WorkspaceFragment.doRestore 链路）解压备份写入配置后直接重启 web，**中间没有依赖同步/校验步骤**。node_modules 未就绪时启动必失败。

**修复建议**：
1. 恢复流程在重启前执行「bundle 完整性检查」，缺失 → 自动 `dsh plugin --profile <p> install` 后再启动
2. 或启动失败时自动重试一次（带依赖修复）
3. 启动结果回传 App（成功/失败 + 原因），失败时给出可操作指引而非静默

---

## 问题 3：「预构件包失败，非法条纹目录」——恢复校验错误信息不可理解 + 无跨版本策略

**现象**：App 1.1.4 恢复旧版本（1.1.2 时代）备份包时提示「预构件包失败，非法条纹目录」，用户无法据此定位问题。

**根因（待源码确认）**：恢复流程对备份包内「预构建包 / stripe 目录」结构做校验，旧格式备份包不满足新校验 → 报错。疑似无版本兼容策略。

**修复建议**：
1. 备份包内写入**格式版本号**（manifest），恢复时按版本走兼容分支：
   - 同版本 → 直接恢复
   - 旧版本 → 提示「备份包格式过旧，建议重新备份」+ 尽力降级恢复
   - 新版本 → 提示「备份包来自更新版本，请升级 App」
2. 错误信息可读化：区分「包损坏」「版本不兼容」「缺关键目录」，并给出下一步操作
3. 校验失败的目录名（stripe/prebuilt）对用户无意义 → 用业务语言描述

## 问题 4：备份包无「自描述」能力，跨版本/跨设备全靠猜

**现象**：备份包只是 tar.gz，无 manifest 说明：来源 App 版本、DSH 版本、profile 名、插件清单、路径结构。

**影响**：恢复流程无法预判兼容性，只能在校验失败时抛笼统错误（问题 3 的根源之一）。

**修复建议**：备份包内加 `backup-manifest.json`：
```json
{
  "formatVersion": 2,
  "appVersion": "1.1.4",
  "dshVersion": "0.1.1-rc.2",
  "profile": "web",
  "bundles": ["dsh-files", "dsh-undo-savepoint", "..."],
  "hasLocalLinks": true
}
```
恢复前读 manifest → 提前决策（兼容/升级/拒绝），比恢复中校验更可靠、提示更友好。

## 参照：dsh-undo-savepoint 已有成熟方案

undo 插件（v0.3.5）已实现跨机迁移安全：
> 恢复前自动预检缺失插件并明确提示；快照可一键导出/导入 ZIP 迁移；恢复后可能缺插件(跨机) → 恢复报告预检提示，先装插件或安全模式

App 备份/恢复流程可直接复用这套设计思路（预检 → 明确提示 → 引导安装）。

## 实测复现记录（2026-08-22 · 应用分身实验）

**实验方法**：
1. 主 App（v1.1.4）重新创建备份（新格式备份包）
2. 系统应用分身（独立 data 目录 + 独立 proot 容器 ≈ 另一台设备）
3. 分身内执行「恢复备份」→ 选新格式包 → 启动 dsh web

**实验结果**：

| 步骤 | 结果 |
|---|---|
| 分身恢复备份（新格式包） | ✅ 通过（未报「预构件包失败」） |
| 分身启动 dsh web | ❌ 失败：`cannot resolve profile bundle "dsh-files"` |

**失败堆栈**（与主设备恢复后偶发错误完全一致）：
```
Error: dsh: cannot resolve profile bundle "dsh-files" from the dsh installation
or /root/.dsh/profiles/web; run 'dsh plugin --profile web install' ...
    at resolveBundleDir (dsh-app-boot/lib/index.js:523)
    at loadProfile (dsh-app-boot/lib/index.js:547)
```

**结论**：
1. **问题 1 跨设备实锤**：备份包内 `dsh-files: link:/root/plugin-src/dsh-files` 本机绝对路径依赖，分身容器（无 /root/plugin-src）恢复后 100% 启动失败。备份未做可移植化。
2. **问题 2 实锤**：恢复流程通过后直接启动，无依赖预检/就绪步骤，失败无自愈。
3. **问题 3 修正**：「预构件包失败，非法条纹目录」仅出现在**旧格式备份包**（v1.1.2 时代 8/21 生成的包）恢复时；新格式包恢复流程通过 → 确认是备份格式无版本兼容策略导致（manifest + 版本分支可解决）。
4. 参照：分身的 dsh web 同样报错 → 与设备、用户、环境无关，纯机制缺陷。
