# DSHA 会话历史损坏（SessionPersistenceCorruptionError）修复记录

> 修复日期：2026-08-22
> 状态：✅ 已修复并验证

---

## 一、问题现象

打开会话时历史加载失败，报错：

```
历史加载失败：history unavailable for session "<会话ID>":
SessionPersistenceCorruptionError: stored session "<会话ID>"
failed validation: Error: session event at seq 987 lacks an identified message（internal）
```

关键信息：**seq 987 的事件缺少标识消息（lacks an identified message）**。

---

## 二、根因分析

### 1. 校验逻辑

DSH 加载会话历史时（`dsh-session` 包的 `Session.fromRestore` → `assertSessionEventEnvelope` → `assertMessageEventShape`），
要求每条 `user/message`、`assistant/message`、`tool/result` 事件必须携带带 `id` 的消息对象：

```js
// @deepseek-ai/dsh-session/lib/index.js:1252
if (typeof message !== "object" || message === null ||
    typeof message["id"] !== "string" || message["id"] === "")
  throw new Error(`${subject} lacks an identified message`);
```

### 2. 损坏点

解压会话文件（zstd 多帧压缩的 JSONL，2066 帧 / 3128 条存储行）后定位到 seq 987：

```json
{
  "type": "user/message",
  "seq": 987,
  "data": {
    "role": "user",
    "content": [{ "type": "text", "text": "【设备操作能力 · DSHA】…（设备引导文本，已省略）" }],
    "source": { "kind": "dsh-device-guide", "plugin": "dsh-device-shell-guide" }
  }
}
```

**`data` 里没有 `id` 字段** → 校验失败 → 整个会话历史拒绝加载。

### 3. 肇事插件

该消息由插件 **`dsh-device-shell-guide`**（DSHA 设备引导插件）注入。
插件通过 `agent/pre-step` 事件向每轮用户消息后插入一条「设备操作指南」，但**手动构造消息对象时漏了 `id`**：

```js
// 修复前（缺 id）：
const guide = {
  role: 'user',
  content: [{ type: 'text', text: PROMPT }],
  source: { kind: 'dsh-device-guide', plugin: 'dsh-device-shell-guide' },
}
```

### 4. 为什么官方插件没这个问题

DSH 官方的消息工厂 `createMessage()`（`@deepseek-ai/dsh-llm`）会自动补身份：

```js
// @deepseek-ai/dsh-llm/lib/index.js:165
function createMessage(input) {
  return freezeMessage({ ...input, id: MessageId(crypto.randomUUID()) });
}
```

官方插件（如 `dsh-compaction-basic`）都用 `createUserMessage()` 建消息，因此天然带 `id`。
本插件手搓消息绕过了工厂 → 消息无 id → 持久化后回放校验失败。

## 三、修复方法

### 修复 1：修复已损坏的会话文件（已执行）

会话文件路径：`<DSH数据目录>/sessions/<会话目录>/session.jsonl.zstd`

步骤：

1. **备份原文件**（保留了两份）：
   - `session.jsonl.zstd.bak-<时间戳>`（原始备份）
   - `session.jsonl.zstd.pre-fix`（改名备份，冗余保留）

2. **解码**：文件是「zstd 多帧容器」（header 帧 + 事件帧，每帧独立可解压、带校验和）。
   用 `node:zlib` 的 `zstdDecompressSync` 逐帧解码，拼接出完整 JSONL 文本。
   帧结构扫描参考 `dsh-session-persistence-jsonl` 的 `scanZstdFrames`（魔数 `0xFD2FB528`）。

3. **修复**：给 seq 987 的 `user/message` 的 `data` 补上 `id`（UUID）：
   ```
   id: <新生成的UUID>
   ```

4. **重写**：header 帧保留原始字节不变；事件部分重新压缩为单帧
   （`zstdCompressSync` + `ZSTD_c_checksumFlag=1`，与 DSH 写入参数一致）。

5. **验证**：用 DSH 自己的代码端到端加载测试：
   ```js
   // JsonlSessionPersistence.loadStored + Session.fromRestore
   // 结果：events=59605（chunk 行展开后），seq=59606，全部通过校验 ✅
   ```

### 修复 2：给插件打补丁，防止复发（已执行）

补丁内容（两处）：

```js
// ① 文件顶部加 import
import { randomUUID } from 'node:crypto'

// ② guide 消息补 id
const guide = {
  id: randomUUID(),          // ← 新增：DSH 要求消息必须带稳定身份
  role: 'user',
  content: [{ type: 'text', text: PROMPT }],
  source: { kind: 'dsh-device-guide', plugin: 'dsh-device-shell-guide' },
}
```

已通过 `node --check` 语法校验。新会话注入的引导消息将带 `id`，不再损坏历史。
（运行中的 DSH 若缓存了旧插件代码，重启后生效。）

## 四、预防与经验

| 要点 | 说明 |
|------|------|
| 消息必须带 `id` | 所有注入/构造的消息务必用官方工厂 `createUserMessage()` 等，或手动补 `id: randomUUID()` |
| 文件结构 | 会话文件是 zstd 多帧容器，修复时按帧解码/重写，header 帧勿动 |
| 备份优先 | 任何修复前先备份原文件，保留双份备份 |
| 验证闭环 | 修复后用 DSH 自身加载路径（loadStored + fromRestore）验证，而非只看格式 |
