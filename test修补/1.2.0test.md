## 1. 3090 本地服务解绑与独立常驻

### 功能说明
3090 端口是 DSHA 内部的原生 HTTP 桥接服务，处理屏幕读屏、点击输入、发送系统通知、提问弹窗等基础能力。这套能力走的是系统无障碍服务，不需要 root，也不需要开启 ADB。在 1.20 重构版本中，上游代码将 3090 服务的启动误绑在无线 ADB 服务（`DeviceBridgeService`）上；如果用户在配置页没开 ADB，3090 端口就不会启动，导致容器内的插件全部因连接被拒而瘫痪。

### 对应代码与实现
在 `HttpShellService.java` 中增加静态启动入口，自带原子防重入锁；并在应用入口 `DshaApp.java` 第一行直接拉起。

**文件**：`app/src/main/java/com/deepseekharness/app/HttpShellService.java`
```java
private static final AtomicBoolean STARTED = new AtomicBoolean(false);

public static void ensureStarted(Context context) {
    if (STARTED.compareAndSet(false, true)) {
        Intent intent = new Intent(context, HttpShellService.class);
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
            context.startForegroundService(intent);
        } else {
            context.startService(intent);
        }
    }
}
```

**文件**：`app/src/main/java/com/deepseekharness/app/DshaApp.java`
```java
@Override
public void onCreate() {
    super.onCreate();
    // 应用启动时无条件启动 3090 本地桥服务
    HttpShellService.ensureStarted(this);
    ...
}
```

## 2. Shizuku 进程管理加固（防僵尸进程与事务死锁）

### 功能说明
通过 Shizuku 执行 root/shell 级别的底层命令时，容易在超时（如运行耗时较长的脚本）或进程异常退出时残留孤儿后台进程，造成电量消耗和端口占用；且跨进程 AIDL 调用如果事务 ID 不固定，跨版本容易发生通信错位。本次将 1.1.10 分支验证过的双轨协同与强杀机制移植进新版。

### 对应代码与实现
**文件**：`app/src/main/java/com/deepseekharness/app/bridge/ShizukuShell.java`
1. **超时与异常时强制斩断远程进程**：
```java
RemoteProcess rp = Shizuku.newProcess(cmd, null, "/");
try {
    // 立即关闭标准输入，防止进程等待控制台输入卡死
    rp.getOutputStream().close();
    boolean finished = rp.waitFor(30, TimeUnit.SECONDS);
    if (!finished) {
        // 超时直接强杀远程进程，杜绝僵尸进程
        rp.destroy();
        return "[TIMEOUT]";
    }
} catch (Exception e) {
    rp.destroy();
    throw e;
}
```
2. **UserService 固化 AIDL 事务编号**：
将 `TRANSACTION_exec` 显式固化为 `1`，`TRANSACTION_destroy` 固化为 `16777114`，并在服务退出时调用 `16777115` 进程自杀协议。

## 3. 状态栏灵动胶囊通知（2003 / 2002 双 ID 接力）

### 功能说明
优化智能体执行任务时的状态栏通知体验，分为互斥的两种状态：
- **运行中通知（ID: 2003，渠道 `dsh_agent_channel`）**：纯静默双耳胶囊 / 灵动岛小胶囊，不弹大白卡，不发提示音，挂载「🛑 停止任务」动作；
- **任务完成通知（ID: 2002，渠道 `dsh_task_result_v2`）**：任务结束时发出高优先级强提醒，弹出浮动大卡片；
- **双 ID 接力清理**：新任务开始时自动清除旧的 2002，任务完成时自动清除 2003，两张卡片绝不重叠；
- **直达抽屉**：点击通知主体或「返回对话」按钮，直接从屏幕底部呼出快捷对话抽屉。

### 对应代码与实现

### 4.3 呼出输入法后顶栏被顶飞出屏幕修复

#### 问题原因
在抽屉里点击输入框呼出软键盘时，顶部的拖拽条、`DSHA 对话` 标题栏、✕ 按钮全部被顶飞到屏幕顶端之外（甚至飞出状态栏），输入框挂在顶部，中间留出大片空白。
1. `ModernAndroidUi` 监听了 `WindowInsets`，键盘一弹起，强行给根视图加了一个键盘高度（1000px）的 `bottomPadding`；
2. `QuickChatSheetActivity.onCreate()` 之前写了 `window.setGravity(Gravity.BOTTOM)`。在 Android 窗口管理器机制下，设置了 `Gravity.BOTTOM` 的 Window 在键盘弹起时，系统会自动将 Window 整体向上平移 1000px；
3. 代码里的 `setupKeyboardObserver` 又手动把底部的 `keyboardSpacer` 垫高了 1000px；
4. 三重位移叠加，卡片顶栏直接被挤到屏幕负坐标处。

#### 对应代码与实现
1. `ModernAndroidUi.java` 豁免后，第一重强推消除；
2. 在 `QuickChatSheetActivity.java` 的 `onCreate()` 中，**彻底移除 `window.setGravity(Gravity.BOTTOM);`**。全屏 Window 默认居顶，卡片底部的停靠完全由内部根布局的 `cardLp.gravity = Gravity.BOTTOM` 控制；
3. 配合 Manifest 的 `android:windowSoftInputMode="adjustNothing"`，键盘弹出时 Window 物理坐标完全静止，卡片顶栏锁死在原位，仅底部的 `keyboardSpacer` 垫高键盘高度，输入框精准停靠在输入法正上方。

### 4.4 调出抽屉时页面全白（401 鉴权死锁）修复

#### 问题原因
从外部拉起抽屉时经常整屏空白：
1. 1.20 移植代码写了一段多余的子线程去异步换 Cookie，在快速拉起抽屉时若 Token 尚未准备好，代码直接用裸地址 `http://127.0.0.1:3080/` 发起请求，被 3080 端口打回 HTTP 401 错误，WebView 渲染成一张白纸；
2. 静态单例 `sCachedWebView` 在 `onNewIntent()` 唤醒时只有位移动画，没有重新加载与自愈逻辑，导致 401 白屏被永久缓存在内存里。

#### 对应代码与实现
**文件**：`app/src/main/java/com/deepseekharness/app/ui/QuickChatSheetActivity.java`
直接加载服务端启动后固定不变的原生 LaunchToken 地址（`controller.getWebAuthUrl()`），移除子线程换 Cookie 逻辑，并在 `onNewIntent` 加入未完成加载时的自动重试：
```java
// 直接加载官方原生带 LaunchToken 的完整地址
String authUrl = controller != null ? controller.getWebAuthUrl() : "";
if (authUrl != null && !authUrl.isEmpty()) {
    sCachedWebView.loadUrl(authUrl);
} else {
    if (progressBar != null) progressBar.setVisibility(View.VISIBLE);
    new Thread(() -> {
        for (int step = 0; step < 30; step++) {
            try { Thread.sleep(300); } catch (InterruptedException ignored) { break; }
            String readyUrl = controller != null ? controller.getWebAuthUrl() : "";
            if (readyUrl != null && !readyUrl.isEmpty()) {
                runOnUiThread(() -> {
                    if (sCachedWebView != null && !isFinishing() && !isDestroyed()) {
                        sCachedWebView.loadUrl(readyUrl);
                    }
                });
                break;
            }
        }
    }, "sheet-wait-auth").start();
}
```

### 4.7 抽屉呼出时主线程死循环与触摸卡死修复

#### 问题原因
真机抓包测得宿主进程主线程 CPU 持续占用达 **50.9%**（直接跑满一颗核心），线程处于 `Running` 状态无法休眠，导致所有点击和滑动无响应。
排查发现：`onReceivedHttpError` 缺少 `request.isForMainFrame()` 判断，且没有防重入锁。页面加载时只要任何一个后台轮询或静态子资源返回 401，就会触发 `view.post(() -> view.loadUrl(retryUrl))`。重载又再次触发子请求报错，导致一秒内上千次 `loadUrl` 涌入主线程消息队列，引发死循环卡死。

#### 对应代码与实现
**文件**：`app/src/main/java/com/deepseekharness/app/ui/QuickChatSheetActivity.java`
增加 `authRetried` 单次锁，并严格限定只对主页面生效：
```java
private boolean authRetried = false;

@Override
public void onReceivedHttpError(WebView view, WebResourceRequest request, WebResourceResponse errorResponse) {
    super.onReceivedHttpError(view, request, errorResponse);
    // 严格限制：仅限主页面 401/403 且仅允许单次重试，绝不处理子资源，彻底根治死循环！
    if (request != null && request.isForMainFrame() && !authRetried) {
        int code = errorResponse != null ? errorResponse.getStatusCode() : 0;
        if (code == 401 || code == 403) {
            authRetried = true;
            String retryUrl = controller != null ? controller.getWebAuthUrl() : "";
            if (retryUrl != null && !retryUrl.isEmpty()) {
                view.post(() -> view.loadUrl(retryUrl));
            }
        }
    }
}
```
在 `onPageFinished` 中重置 `authRetried = false`。

### 4.8 点击通知开抽屉留空修复

#### 问题原因
通过 `dumpsys activity activities` 现场抓包发现：系统里同时存在两个不同类的任务栈：
- `Task #19: com.deepseekharness.app.ui.QuickChatSheetActivity`
- `Task #24: com.deepseekharness.app.QuickChatSheetActivity`
因为两个同名组件都在 `AndroidManifest.xml` 中注册，且争夺同一个静态 `sCachedWebView`。通知栏拉起组件 B 时把静态 View 移入了新窗口；当组件 A 再次回到前台走 `onNewIntent` 时，由于 `onNewIntent` 只有位移动画没有重新挂载 View，导致组件 A 的容器完全留空。

#### 对应代码与实现
1. **删除冗余类，改用官方 `activity-alias`**：
   - 彻底删除 `app/src/main/java/com/deepseekharness/app/QuickChatSheetActivity.java`；
   - 在 `AndroidManifest.xml` 中将原本重复的 `<activity>` 替换为 `<activity-alias>`，命令行和通知统一路由到同一个真实组件：
```xml
<activity
    android:name=".ui.QuickChatSheetActivity"
    android:exported="true"
    android:taskAffinity="com.dsh.client.quick_sheet"
    android:excludeFromRecents="true"
    android:launchMode="singleInstance"
    android:windowSoftInputMode="adjustNothing"
    android:theme="@style/Theme.DeepseekHarness.SheetTransparent" />
<activity-alias
    android:name=".QuickChatSheetActivity"
    android:targetActivity=".ui.QuickChatSheetActivity"
    android:exported="true" />
```
2. **在 `onNewIntent` 强制保证 View 挂载完整**：
```java
@Override
protected void onNewIntent(Intent intent) {
    super.onNewIntent(intent);
    setIntent(intent);
    if (sCachedWebView != null) {
        if (sCachedWebView.getParent() != webContainer) {
            if (sCachedWebView.getParent() instanceof ViewGroup) {
                ((ViewGroup) sCachedWebView.getParent()).removeView(sCachedWebView);
            }
            webContainer.addView(sCachedWebView, new FrameLayout.LayoutParams(
                    ViewGroup.LayoutParams.MATCH_PARENT, ViewGroup.LayoutParams.MATCH_PARENT));
        }
        ...
    }
    animateIn();
}
```

## 5. Shizuku 授权提示找不到应用（无法握手）修复

### 问题原因
在真机上已安装 Shizuku，但在工作区点击“授权 Shizuku”时毫无反应，提示“请先安装并启动 Shizuku”。
Shizuku 的跨进程原理是**由客户端自己暴露 `${applicationId}.shizuku` ContentProvider 作为接收特权 Binder 的握手通道**。上游在 1.20 重构时：
1. 误删了 `AndroidManifest.xml` 里的 `rikka.shizuku.ShizukuProvider`，关闭了接收 Binder 的通道；
2. 在 `app/build.gradle` 中将 Shizuku SDK 版本倒退为老旧的 `12.2.0`（原版为 `13.1.5`）。

### 对应代码与实现
1. **在 `AndroidManifest.xml` 的 `<application>` 节点内补回 Provider 声明**：
```xml
<provider
    android:name="rikka.shizuku.ShizukuProvider"
    android:authorities="${applicationId}.shizuku"
    android:multiprocess="false"
    android:enabled="true"
    android:exported="true"
    android:permission="android.permission.INTERACT_ACROSS_USERS_FULL" />
```
2. **在 `app/build.gradle` 中恢复 SDK 版本至 13.1.5**：
```groovy
implementation 'dev.rikka.shizuku:api:13.1.5'
implementation 'dev.rikka.shizuku:provider:13.1.5'
```

## 6. 全场景任务中断统一监听与异常兜底

### 功能说明
解决各种任务中断情况下通知无法捕获、通知栏静默消失或将偷懒敷衍误报为“任务完成”的问题：
- **人为停止**：无论是在通知栏点停止还是外部中止，不再静音，100% 弹出通知明确提示「⚠️ 任务已终止」；
- **模型偷懒**：如果模型没有输出任何实质动作/文字就停下，不再误报为完成，而是明确提示「⚠️ 智能体未完成任务」；
- **底层崩溃**：接入 Cordis 全局 `agent/error` 事件总线，捕获脱离普通会话流的底层致命崩溃；
- **终极兜底**：在 `turn/end` 结算处设立严格的“反转白名单”，凡是没有被明确识别为成功交付的其余所有意外，一律统一弹出「⚠️ 任务异常中断」。
所有中断通知统一走系统的高优先级结果通道：`Constants.CHANNEL_TASK_RESULT`（ID: 2002），唤醒用户并提供「返回对话」直达抽屉。

**文件**：`app/src/main/assets/task-notifier/lib/index.js`
```javascript
export const name = 'dsh-task-notifier'
export const inject = []

export function apply(ctx) {
  ...
  // 1. 监听 session/event 的 turn/end 终局收口
  ctx.on('session/event', (session, event) => {
    ...
    if (type === 'turn/end') {
      if (trailingTimer) { clearTimeout(trailingTimer); trailingTimer = null; }
      pendingState = null
      if (session?.parentSessionId || session?.parent) return; // 忽略子任务单独结束

      const reasonObj = event.data?.reason
      const kind = reasonObj?.kind ?? 'completed'

      if (kind === 'error') {
        const detail = parseFailureDetail(reasonObj?.error)
        void callBridge('/app/notify', {
          title: '❌ 模型请求失败',
          text: detail || '服务请求异常，点击或在下方打字重试'
        })
        return
      }

      if (kind === 'aborted') {
        // 彻底废除静音拦截：通知栏点击停止或外部中止，一律弹出终止通知
        void callBridge('/app/notify', {
          title: '⚠️ 任务已终止',
          text: '已按指令停止操作，点击查看或继续对话'
        })
        return
      }

      if (kind === 'max-tokens') {
        void callBridge('/app/notify', {
          title: '📏 达到最大长度',
          text: '已达单次最大输出限制，可发送“继续”接着生成'
        })
        return
      }

      if (kind === 'blocked') {
        void callBridge('/app/notify', {
          title: '🛡️ 任务已挂起',
          text: '等待安全授权或前置条件处理'
        })
        return
      }

      if (kind === 'interrupted') {
        void callBridge('/app/notify', {
          title: '⚡ 连接异常中断',
          text: '与容器连接丢失，点击重新进入'
        })
        return
      }

      if (kind === 'completed') {
        // 严防模型偷懒：若未输出任何实质文本或内容全为空白，绝不能判定为成功完成
        if (!lastAssistantText || !lastAssistantText.trim()) {
          void callBridge('/app/notify', {
            title: '⚠️ 智能体未完成任务',
            text: '模型已停下但未输出有效动作，点击返回对话'
          })
          return
        }

        const clean = lastAssistantText.replace(/\s+/g, ' ').trim()
        const endText = clean.length > 60 ? clean.slice(0, 60) + '…' : clean
        void callBridge('/app/notify', {
          title: '任务已完成',
          text: endText
        })
        return
      }

      // 统一终极兜底：所有未明确归类或意外脱轨的中断情况，一律弹中断通知
      const detail = parseFailureDetail(reasonObj?.error) || String(kind || '任务中途脱轨或意外中断')
      void callBridge('/app/notify', {
        title: '⚠️ 任务异常中断',
        text: `${detail}，点击返回对话查看`
      })
    }
  })

  // 2. 监听全局 agent/error 异常广播（捕获脱离会话流的底层致命崩溃）
  ctx.on('agent/error', ({ agent, error }) => {
    try {
      if (trailingTimer) { clearTimeout(trailingTimer); trailingTimer = null; }
      pendingState = null
      const detail = parseFailureDetail(error)
      void callBridge('/app/notify', {
        title: '⚠️ 任务异常中断',
        text: detail || '智能体运行时发生底层故障中断'
      })
    } catch {}
  })
}
```

## 10. 状态栏灵动胶囊文本截断与「⚠️任务终止」显示优化

### 问题原因
在真机小米澎湃 OS（HyperOS）上，智能体任务终止时，顶部灵动岛右侧胶囊显示异常，文字被切成“⚠️ 任…”。
经排查：
1. `HttpShellService.java` 中的 `compactCapsuleText(detail)` 关键词匹配列出了“中断”、“停止”、“cancel”，但**漏掉了“终止”关键词**；
2. Java 字符串切片对包含 Emoji（如 `⚠️` 占 2 个 char）及空格的字符串直接调用 `s.substring(0, 4)`，Emoji 和空格耗尽了前 3 个字符位，刚好切在“任”字后面，代码自己生成了带有省略号的“⚠️ 任…”送给系统。

### 对应代码与实现
**文件**：`app/src/main/java/com/deepseekharness/app/HttpShellService.java`
1. 显式增加对“终止”关键词的匹配，返回紧凑的 **`⚠️任务终止`**（视觉宽度刚好等同于“任务已完成”的 5 汉字物理界限，无多余空格，100% 完整展示不被截断）；
2. 增加“⚠️未完成”、“❌执行失败”、“📏长度超限”等紧凑标签映射；
3. 兜底截断逻辑中增加前导符号/空格剥离，杜绝字符切碎问题。
